# 文档规格

合成正文前通读本文。规格分五部分：读者模型（一切规则的根）、骨架（写哪些章节）、图文节拍（图和文怎么配合）、旅程写法（核心章节怎么写）、写作规则（全文遵循）。

## 读者模型

文档写给一个**没有看过这个 PR 任何 diff** 的读者。用连贯流畅的语言、清晰的逻辑，深入浅出地让他从宏观到细节完整理解这个 PR 做了什么、为什么这么做。文档可以长，但必须有序。

「可以长」不只是文档层的许可，更要落到句子层：宁可多花三个句子把一件事讲清，不写一个三层嵌套的长句。篇幅焦虑是急迫感的来源，而急迫感是走查文档的头号敌人。

两个验收问题：

1. 读完之后，读者对这个项目的理解需要改哪几处？
2. 将来出问题，读者知道从哪个文件、哪个函数下手排查吗？

衡量标准：**读者能否凭文档在代码里定位**。做不到这一点的段落是摘要腔，重写。

自包含红线：读者一次线性读完，不点任何链接、不回看任何代码，也能建立完整的心智模型。代码片段与画板是理解的加速器，不是必经门；文件级指路可以给（成本低），但正文的论证绝不依赖读者真的回去读。

## 骨架

完整骨架如下，章节按情况伸缩（见「伸缩规则」）。

| # | 章节 | 内容 | 飞书组件 |
|---|------|------|----------|
| 1 | 导读 | 文档开头一个 callout：PR 规模（行数 / commit 数 / 测试规模）、产出方法一句话、阅读路径建议 | callout |
| 2 | TL;DR | ≤5 行讲清干了什么 + 为什么做（动机来自文档或 commit 推断） | 段落 |
| 3 | 变更地图（称重） | 各子系统变更量；每个子系统两列——"设计重心（要细读）"和"可放心略过"；测试占比。称重要诚实：结论可以是"几乎全是设计承载代码"，不为安抚而把 PR 说小 | 表格 |
| 4 | 架构一图流 | before/after 结构对比。仅当通信结构、分层、进程角色等架构面变化时保留 | 画板 |
| 5 | 数据与状态先行 | 新增/变更的类型、协议消息、状态容器——只看形状不讲行为，给后续旅程预载词汇 | 代码块 + 表格 |
| 6 | 底座 | 多条旅程共用的机制走读（如调用链、错误管线、凭证、生命周期），旅程里只讲各自特有逻辑 | 走读式 |
| 7 | 旅程 ×N | 核心章节，见「旅程写法」。条数按 PR 的主要用户可见行为定，通常 2–4 条 | 见下 |
| 8 | 计划 vs 实现的偏差 | 仅自己的、带随附文档的 PR。每条 = 计划是什么 / 实际做成什么 / 为什么变。只收实质偏差，结论内联自包含 | 表格 |
| 9 | 心智模型补丁 | "以前可以假设 X，现在必须 Y"，控制在 5–8 条 | 列表或表格 |
| 10 | 新词表 | 仅本 PR 新增的词，按域分组，每词一句白话。不跨 PR 累积 | 表格 |
| 11 | 测试与风险 | 两列："有兜底的"（哪些行为有测试钉住）和"薄冰"（重要逻辑无测试、已知遗留）。纯事实陈述。合并前必办事项用 checkbox 列出。结尾附"别被这些吓到"清单：无挂载点的组件、只有接口没有生产者的预留、git 误判的 rename 等，防读者验收时误判为缺陷 | 列表 + checkbox |

### 伸缩规则

- **篇幅跟设计密度走，不跟行数走**。万行机械迁移的文档可以比八百行精巧改动的更短。
- **小 PR（< ~1,000 行）**：压缩为 TL;DR → 一条旅程 → 心智模型补丁 → 新词表（如有）→ 测试与风险。砍掉导读、地图、架构图、底座。
- **别人的 PR**：无第 8 章（没有随附文档可挖）；关键设计点处可以加**一句**"为什么不是直觉做法"——读者没参与过设计讨论，没这句只能看到结果看不到判断。仅一句，不展开备选方案。
- **自己的 PR**：第 8 章是高价值章节——照计划做成的部分读者已知，偏差才是认知裂缝。偏差从 run log / followups / commit message 里挖（"fix:"、"instead"、"rework" 这类字眼是变卦的尸检报告）。
- **PR 类型决定叙事框架**：重构 → 旅程讲"同一个用户操作，旧管线 vs 新管线"；功能 → 讲"多了一条新旅程"；修复 → 讲"原来错在哪、为什么会错"。

## 图文节拍

状态机、闸门、管线、泳道、时序这类**图状信息，禁止让线性文字独自承担**。文字是线性的，图状结构塞进线性通道，读者只能在脑内自己重新画图；既然要画图，就把图直接给他，而且给在前面。

结构性内容的小节节拍固定为四拍：

1. 一句话点题：这一节回答什么问题。
2. 画板：给出结构骨架。
3. 正文沿着图走一遍：读者眼睛在图上，文字负责导游。
4. 讲图讲不了的 why：为什么长这样、拒绝了什么替代方案、边界在哪。

图先给骨架，文字只在骨架上挂血肉。非结构性内容（单个判据、一条契约）不强配图。

画板全文 3–6 张，每张只回答一个问题；一张图想塞两个主题时，拆成两张。结构隐喻要与机制同构（闸门串联就画闸门、状态流转就画状态机），不是装饰。规划与插入流程见 SKILL.md 第六步——写作顺序上画板后置不影响文档顺序上图先行，锚点选在点题句之后即可。

## 手段选择表

每个小节由一个读者问题驱动；贴代码还是画图不是风格偏好，按信息的形状选：

| 信息的形状 | 手段 |
|-----------|------|
| 概念、领域模型 | 白话 + 类比 + 表格 |
| 图状结构（状态机、闸门、管线、时序） | 画板先行，正文沿图走 |
| 判据、不变式，≤20 行代码能自明 | 真实代码片段：亲自 Read 过、亲手裁剪，caption 标注所在文件 |
| 更长的流程逻辑 | 不贴长代码。契约伪码蒸馏，或改画图 |

**契约伪码**：把上百行实现蒸馏成十行以内、只保留不变式与关键分支的伪码，caption 指向真实文件。它回答"这段机制承诺了什么"，不回答"代码逐行怎么写"。读者需要后者时自会去看文件。

## 旅程写法

旅程 = 沿一个用户操作（或一类事件）把代码流转走通。每条旅程固定三段式：

**1. 全景**：旅程开头给途经环节一览——一行文字列出环节与文件；复杂旅程（跨进程、多参与方）用画板。先定位再下潜。

**2. 逐跳放大**：按执行顺序推进，每跳一个小节。每跳的标准节拍：

- 先用一两句把这一跳的问题或场景摆清楚（竞态先画时间线、坑先说后果）；
- 再上手段选择表选定的载体，叙述与代码/图交替——不许"上面讲故事、下面堆代码"两张皮；
- 复杂机制分层拆：场景设定 → 第一层 → 第二层 → ……每层一段叙述配一段载体。**一段话只讲一件事**；
- 改动过的流程用前后对比讲，before 必须基于 base 侧真实代码，不凭 diff 猜。

**3. 排查路标**：旅程收尾必备。一张两列表：可观察的症状 → 去哪个文件看哪个函数/哪个状态。这是"控制感"的直接载体——读者读完不只是"知道了"，而是"出事知道从哪下手"。

## 写作规则

每条规则都写了目的。理解目的比背条文重要：拿不准某句话该不该这样写时，回到目的判断。

### 段落层

1. **解析不是摘要**。一段只讲一件事；禁止用一段话罗列多个机制；禁止 `A → B → C 失败` 式箭头链压缩——箭头链只允许出现在全景和图里，正文必须展开。
2. **代码一手原则**。文档中出现的每段代码必须出自亲自 Read 过的文件，亲手裁剪（可用 `// ...` 省略无关行，单段 ≤20 行）；每段代码用 caption 标注所在文件。**禁止引用 subagent 转述的代码**。
3. **自包含**。不要求读者读任何外部文档；随附文档只作输入矿源，结论一律内联。不写"详见 xxx.md"。
4. **指路不承重**。位置引用到文件/模块粒度，不贴行号。指路是给想深挖的读者的赠品，正文的论证不依赖读者真的去读。
5. **禁不可观察描述**。"重构了 X""优化了 Y""改进了 Z"一律禁止，必须说出可观察的变化（"以前溢出静默关流，现在溢出抛错"）。
6. **新词白话**。任何不能假设读者已知的名词，首次出现必须带一句白话解释。
7. **不挑刺**。不评代码风格、不提改进建议——code review 有专门流程。"重要逻辑没有测试兜底"属于事实陈述，写入第 11 章。

### 句子层

目的先行：读者的工作记忆是个很浅的栈。每个分号、括号、破折号都在往栈里压新帧，压到第三层，前面的就丢了——"似懂非懂"就是栈溢出的体感。精读之后什么都觉得重要，于是用标点把八个机制压进一个句号，这是走查文档最常见的劣化路径。密度要靠取舍控制，不靠标点压缩。

8. **括号里只放名词性内容**：代号、枚举、文件名。括号内容一旦含谓语，它就是一个被压扁的句子——拉出来独立成句，或者删掉。
9. **破折号后不接完整从句**，一段至多一个破折号。补充理由用"因为""否则"起新句。
10. **一句话承载一件事**。超过约 80 字、或出现两层以上嵌套，就拆句。
11. **允许刻意冗余**。复杂机制讲完，允许一句"换句话说"式的白话复述；章节结尾允许一句小结。教学性文本的冗余不是浪费，是读者固化理解的台阶。

反面标本与改法（真实案例裁剪）：

> ❌ 新实现只保留一次 ls-files 枚举，之后全部是文件系统直读：并发 8、批内并行批间保序；每路径先词法 containment 再 lstat，symlink 不跟随、readlink 的链接文本即内容（这正是 git 自己的 symlink diff 语义，同时封死「未跟踪 symlink 指向 workspace 外」的读穿向量）；二进制判定用前 8000 字节嗅探 NUL——8000 而不是 8192，是对齐 git 自身启发式的常量。

一个句号八个机制，读者的栈在第三个分号处就溢出了。拆开：

> ✅ 新实现里 git 只出场一次：用 ls-files 枚举出未跟踪文件的清单。之后每个文件都由文件系统直读，不再起任何进程。
> 读文件之前有两道防线。先做路径包含检查，确认目标在 workspace 之内。再识别 symlink：不跟随目标，把链接文本本身当作内容。这正是 git 自己的 symlink 语义，顺带封死了一类攻击，即用一个指向 workspace 外的 symlink 借 diff 读出外部文件。
> 二进制判定沿用 git 的启发式：读前 8000 字节，见到 NUL 就算二进制。

字数多三成，认知负担少一半。这就是"可以长"在句子层的含义。

### 飞书组件

- callout 只用于全文级提醒（导读、合并前必办一类），全文不超过 3 个。满屏高亮等于没有高亮。
- 表格用于真正可枚举的事实；解释放正文，不塞进单元格。
- 待办、待拍板事项用 checkbox。
- 代码块带 lang 与 caption，caption 标注来源文件或命令。
- 具体 XML 语法与写入命令以 lark-doc skill 为真相源，本文不重复。
