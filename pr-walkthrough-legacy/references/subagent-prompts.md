# Subagent 编排与 prompt 模板

大型 diff（> ~5,000 变更行）分发 subagent 精读时使用本文。模板中 `{占位符}` 按实际情况填充。

## 编排要点

- **划分**：按 monorepo 顶层目录/包切分，一个子系统一个 agent；单个 agent 的范围控制在 ~8,000 变更行以内，超了再切。
- **兜底**：安排一个「杂项 agent」覆盖主目录之外的一切（依赖 manifest、lockfile、脚本、CI、根配置、README/AGENTS 类文档）——确保每一行改动都在某个 agent 的视野内，无死角。
- **文档矿工**：仅当 PR 带随附文档（技术方案、执行计划、run log、遗留清单）时增派一个，挖"计划 vs 实现偏差"。
- **并行**：全部 agent 在同一条消息里一次性发出。
- **产出定位**：subagent 的最终输出是给编排者的素材，不是面向用户的文章——prompt 里已写明，收到后按密度阅读即可。
- **收到素材后**：素材只作地图（哪里重要、结论是什么）。报告里出现的代码必须由主 agent 二次精读对应文件后亲手裁剪（见 SKILL.md 第四步），不直接引用素材里的代码转述。

## 子系统精读模板

```
你在分析一个大型分支 diff 的其中一个子系统，为项目 owner 产出「PR 理解报告」的原始素材。
这不是 code review——不挑刺、不提改进建议、不评风格，只负责让人理解。

仓库：{repo_path}（对比基线 {base}）。项目背景：{一句话项目定位 + monorepo 结构一句话}。
本分支主题：{一句话，没有则写"以代码为准"}。

你的子系统：**{scope_path}**（约 {N} 行变更）。{该子系统的角色一句话；如有应特别关注的面，
在此点名，例如"注意 main/preload/renderer 三层的角色分配有没有变"}。

工作方式：
- `git -C {repo_path} diff {base}...HEAD --numstat -- {scope_path}` 先看文件清单和权重
- 逐文件精读 diff（`git -C {repo_path} diff {base}...HEAD -- {scope_path}/<file>`）。
  **必须覆盖全部文件**，量大就分批读，不许略读跳过。
- before 状态不要凭 diff 猜：`git -C {repo_path} show {base}:<path>` 看旧代码原貌；
  after 状态可直接读工作区文件补上下文。

输出（中文，代码保持原文），按以下结构，长度不限、信息要密：

1. **总括**：本子系统改动一句话 + before/after 结构对比（以前这个目录长什么样、按什么分层；现在长什么样）。
2. **机械 vs 设计分拣**：哪些文件是搬运/重命名/样板/生成物（列出、归类、粗略行数），哪些承载真实设计。
3. **数据与状态形状**：新增/修改的类型、接口、协议消息、内存状态结构——贴关键类型定义片段。
4. **关键设计点**（数量不限，按密度来）：每个 = 白话解释 + 从 diff 裁剪的代码片段（≤30 行，可用 // ... 省略）
   + 所在模块 + 标注是新先例还是复用既有 pattern。
5. **控制流进出口**：外部如何调进本子系统、本子系统调出到哪。给出 2-3 条「一个典型请求/事件穿过
   本子系统的逐步路径」，并对每条给出 before 管线 vs after 管线的步骤对比（before 从 {base} 侧代码确认）。
6. **新名词**：本 diff 引入的新类/新概念/缩写，每个一句白话解释。
7. **测试覆盖**：新增/修改了哪些测试、分别覆盖什么行为；哪些重要新逻辑没有测试兜底（事实陈述即可）。
8. **存疑处**：你没完全看懂或可疑的地方，如实列出。

硬规则：不贴行号（不写 file.ts:123）；位置到文件/模块粒度；禁止「重构了X」「优化了Y」这种
不可观察的描述，必须说出可观察的变化；任何非通用术语首现带一句白话。
你的最终输出是给编排者的素材，不是面向用户的文章，按数据密度写。
```

## 文档矿工模板

```
你在为一份「PR 理解报告」挖原始素材。这个 PR 是 {一句话主题}，实现分支 {branch}
（仓库 {repo_path}，对比 {base}），重构/开发全程有随附文档。你的任务是把
「计划是什么、实际做成了什么、中途哪里变了卦」挖出来，结论必须自包含——读者不会去读这些文档原文。

要读的文档：
{文档路径列表}

另外扫一遍 commit 信息（只看 message 不看 diff）：
`git -C {repo_path} log --format='%h %s%n%b---' {base}..HEAD`
从中嗅偏差线索（"fix:"、"rework"、"instead" 这类字眼往往是中途变卦的尸检报告）。

输出（中文），结构：

1. **动机与目标**：为什么做、要达到什么状态（白话，两三句，自包含）。
2. **计划的阶段结构**：各阶段一句话意图。
3. **计划 vs 实现的偏差清单**（重头戏）：每条 = 计划原本是什么 / 实际做成了什么 / 为什么变。
   只收实质偏差，措辞自包含，不写「见 xxx 文档」。
4. **已知遗留问题**：文档里列的待办和已知坑，每条一句白话 + 严重程度（如有标注）。
5. **过程元信息**（简短）：实现过程怎么组织的，一两句即可。

硬规则：所有结论自包含、白话；不贴行号；非通用术语首现带解释。
输出是给编排者的素材，按数据密度写。
```
