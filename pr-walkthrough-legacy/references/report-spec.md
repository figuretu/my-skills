# 报告规格

合成报告前通读本文。规格分三部分：骨架（写哪些章节）、旅程写法（核心章节怎么写）、写作硬规则（全文红线）。

## 定位

报告不是 diff 摘要，是「读者心智模型的增量更新」。摘要回答"这个 PR 改了什么"；本报告回答两个问题：

1. 读完之后，我对这个项目的理解需要改哪几处？
2. 将来出问题，我知道从哪个文件、哪个函数下手排查吗？

衡量标准：**读者能否凭报告在代码里定位**。做不到这一点的段落是摘要腔，重写。

## 骨架

完整骨架如下，章节按情况伸缩（见各条说明与「伸缩规则」）。模板组件名指 `assets/template.html` 中的对应组件。

| # | 章节 | 内容 | 组件 |
|---|------|------|------|
| 1 | TL;DR | ≤5 行讲清干了什么 + 为什么做（动机来自文档或 commit 推断） | 段落 |
| 2 | 变更地图（称重） | 各子系统变更量条形图；每个子系统两列——"设计重心（要细读）"和"可放心略过"；测试占比。称重要诚实：结论可以是"几乎全是设计承载代码"，不为安抚而把 PR 说小 | bar-row + 表格 |
| 3 | 架构一图流 | before/after 双栏通道图。仅当通信结构、分层、进程角色等架构面变化时保留 | arch |
| 4 | 数据与状态先行 | 新增/变更的类型、协议消息、状态容器——只看形状不讲行为，给后续旅程预载词汇。每个形状配类型定义片段 | codecap + pre |
| 5 | 底座 | 多条旅程共用的机制走读（如调用链、错误管线、凭证、生命周期），旅程里只讲各自特有逻辑。含"新增 X 的标准步骤"配方（callout） | 走读式 |
| 6 | 旅程 ×N | 核心章节，见「旅程写法」。条数按 PR 的主要用户可见行为定，通常 2–4 条 | 见下 |
| 7 | 计划 vs 实现的偏差 | 仅自己的、带随附文档的 PR。每条 = 计划是什么 / 实际做成什么 / 为什么变。只收实质偏差，结论内联自包含 | 双列表格 |
| 8 | 心智模型补丁 | "以前可以假设 X，现在必须 Y"，每条一张卡，控制在 5–8 条 | patch |
| 9 | 新词表 | 仅本 PR 新增的词，按域分组，每词一句白话。不跨 PR 累积 | 分组表格 |
| 10 | 测试与风险地图 | 两列清单："有兜底的"（哪些行为有测试钉住）和"薄冰"（重要逻辑无测试、已知遗留，标 🔴🟠🟡⚪）。纯事实陈述。合并前必办事项放 callout warn | 列表 + callout |
| 11 | 验收提示 | "别被这些吓到"：无挂载点的组件、只有接口没有生产者的预留、git 误判的 rename 等——防止读者验收时误判为缺陷 | 列表 |
| 12 | 覆盖声明 | 谁读了什么、是否全量、有无略读。诚实声明，不让报告读起来像精读过实际只是抽查 | 段落 |

### 伸缩规则

- **篇幅跟设计密度走，不跟行数走**。万行机械迁移的报告可以比八百行精巧改动的更短。
- **小 PR（< ~1,000 行）**：压缩为 TL;DR → 一条旅程 → 心智模型补丁 → 新词表（如有）→ 测试。砍掉地图、架构图、底座。
- **别人的 PR**：无第 7 节（没有随附文档可挖）；关键设计点处可以加**一句**"为什么不是直觉做法"——读者没参与过设计讨论，没这句只能看到结果看不到判断。仅一句，不展开备选方案。
- **自己的 PR**：第 7 节是高价值章节——照计划做成的部分读者已知，偏差才是认知裂缝。偏差从 run log / followups / commit message 里挖（"fix:"、"instead"、"rework" 这类字眼是变卦的尸检报告）。
- **PR 类型决定叙事框架**：重构 → 旅程讲"同一个用户操作，旧管线 vs 新管线"（vs-grid）；功能 → 讲"多了一条新旅程"；修复 → 讲"原来错在哪、为什么会错"。

## 旅程写法（核心）

旅程 = 沿一个用户操作（或一类事件）把代码流转走通。每条旅程固定三段式：

**1. 全景条（overview 组件）**：旅程开头一行列出途经环节和文件，先定位再下潜。不需要展开的环节用 `hop plain`。

**2. 逐跳放大**：按执行顺序推进，每跳一个 h3 小节。每跳的标准节拍：

- 先用一两句把这一跳的问题或场景摆清楚（竞态先画时间线、坑先说后果）；
- 再上该处的真实代码（codecap + pre），叙述与代码交替——不许"上面讲故事、下面堆代码"两张皮；
- 复杂机制分层拆：场景设定 → 第一层 → 第二层 →……每层一段叙述配一段代码。**一段话只讲一件事**——一段话里塞十个机制是摘要腔的典型症状；
- 改动过的流程用前后对比讲（vs-grid），before 必须基于 base 侧真实代码，不凭 diff 猜。

**3. 排查路标（waypoint 组件）**：旅程收尾必备。一张两列表：可观察的症状 → 去哪个文件看哪个函数/哪个状态。这是"控制感"的直接载体——读者读完不只是"知道了"，而是"出事知道从哪下手"。

## 写作硬规则（全文红线）

1. **解析不是摘要**。一段只讲一件事；禁止用一段话罗列多个机制；禁止 `A → B → C 失败` 式箭头链压缩——箭头链只允许出现在全景条和对比图里，正文必须展开。
2. **代码一手原则**。报告中出现的每段代码必须出自亲自 Read 过的文件，亲手裁剪（可用 `// ...` 省略无关行，单段一般 ≤30 行）。解读注释（`.a` 青色）与源码原注释（`.c` 灰色）视觉区分；每段代码用 codecap 标注所在文件。**禁止引用 subagent 转述的代码**。
3. **自包含**。不要求读者读任何外部文档；随附文档只作输入矿源，结论一律内联。不写"详见 xxx.md"。
4. **不贴行号**。不写 `file.ts:123` 式引用；位置到文件/模块粒度。
5. **禁不可观察描述**。"重构了 X""优化了 Y""改进了 Z"一律禁止，必须说出可观察的变化（"以前溢出静默关流，现在溢出抛错"）。
6. **新词白话**。任何不能假设读者已知的名词，首次出现必须带一句白话解释。
7. **不挑刺**。不评代码风格、不提改进建议——code review 有专门流程。"重要逻辑没有测试兜底"属于事实陈述，写入第 10 节。
8. **图怎么直观怎么来**。架构用 arch 双栏，流程对比用 vs-grid，全部用模板内置组件实现，不依赖 mermaid 等外部渲染。

## 模板使用

- 复制 `assets/template.html` 的完整 `<style>` 与页面结构，**CSS 不改**（保证历次报告视觉一致）。
- 左侧 `nav.toc` 必须保留，条目与正文 h2 锚点一一对应；长章节的关键小节用 `class="sub"` 加二级条目。
- 组件按内容增删实例；各组件用途见模板内注释。
- 代码内 HTML 特殊字符（`<` `>` `&`）必须转义。
- 页头保留"写法说明"一段（向读者说明注释颜色约定与排查路标）。
